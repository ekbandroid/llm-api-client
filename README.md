# llm-cli

Минимальный консольный чат с LLM через OpenAI-совместимый API. Хранит историю диалога в рамках сессии.

## Установка

```bash
git clone https://github.com/ВАШ_ЛОГИН/llm-cli.git
cd llm-cli

python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

## Настройка

```bash
cp .env.example .env
```

Откройте `.env` и впишите свой ключ. Файл `.env` в `.gitignore`, в репозиторий он не попадёт.

## Запуск

```bash
python app.py
```

## Другие провайдеры

Приложение работает с любым API, совместимым с форматом OpenAI. Меняются только две переменные в `.env`:

| Провайдер | `LLM_BASE_URL` | `LLM_MODEL` |
|---|---|---|
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| DeepSeek | `https://api.deepseek.com` | `deepseek-v4-flash` (дешёвая) / `deepseek-v4-pro` |
| OpenRouter | `https://openrouter.ai/api/v1` | `anthropic/claude-sonnet-4.5` |
| Ollama (локально) | `http://localhost:11434/v1` | `llama3.2` |

Названия моделей меняются — актуальные смотрите в документации провайдера.

## Сравнение ответов: без ограничений и с ограничениями

```bash
python compare.py                          # вопрос по умолчанию
python compare.py "ваш вопрос"             # свой вопрос
```

Скрипт отправляет **один и тот же вопрос дважды** и печатает оба ответа с таблицей метрик.

| | Без ограничений | С ограничениями |
|---|---|---|
| Формат | не задан | жёсткая схема ТЕЗИС / ПРИЧИНЫ / ВЫВОД в системном промпте |
| Длина | не задана | лимит 80 слов в промпте + `max_tokens=250` на стороне API |
| Завершение | по усмотрению модели | `stop=["###END###"]` + инструкция вывести этот маркер |

Ограничения задаются на двух уровнях, и это не дублирование: инструкция в промпте
заставляет модель *планировать* короткий ответ, а `max_tokens` и `stop` — страховка
на стороне API на случай, если инструкцию проигнорируют.

Поле `finish_reason` в таблице показывает, чем кончилась генерация: `stop` — модель
завершила ответ сама, `length` — упёрлась в `max_tokens` и ответ оборван на полуслове.

### Подводный камень с thinking

У рассуждающих моделей (вся линейка DeepSeek v4) `max_tokens` ограничивает
рассуждение и ответ **вместе**. При включённом thinking рассуждение съедает весь
бюджет, и приходит пустой `content` с `finish_reason: length`. Причём отсутствие
поля `thinking` в запросе такую модель не выключает — нужно явно передать
`{"type": "disabled"}`, что и делает `llm.py`. Поэтому `compare.py` считает
без thinking: иначе сравнение длины ответов теряет смысл.

## Веб-интерфейс

```bash
uvicorn web:app --reload
```

Откройте http://127.0.0.1:8000

Ответ приходит **потоком** (SSE): текст появляется по мере генерации, а не после
полной готовности. На запросах в десятки секунд это принципиально меняет ощущение
от интерфейса.

Все ограничения из раздела выше выставляются прямо на странице:

| Панель | Что задаёт | Куда уходит |
|---|---|---|
| Модель | какая модель отвечает | поле `model` запроса |
| Режим thinking | рассуждать или нет | `thinking: {"type": ...}` |
| Формат ответа | пресет или своя инструкция | системный промпт |
| Лимит слов | «не более N слов» | системный промпт |
| `max_tokens` | жёсткий потолок генерации | параметр API |
| Стоп-последовательность | где оборвать | `stop` + инструкция в промпте |

Под каждым ответом — телеметрия: `finish_reason`, расход токенов, число слов,
время. Собранный системный промпт показан там же в сворачиваемом блоке, так что
видно, во что именно превратились выставленные переключатели. Если генерацию
оборвал `max_tokens`, выводится предупреждение — при включённом thinking с этим
сталкиваешься быстро.

История диалога живёт **только в памяти вкладки**: сервер не хранит ничего,
перезагрузка страницы очищает переписку. Состояния на сервере нет вовсе — весь
диалог приходит с каждым запросом.

## Доступ: регистрация и подтверждение

Чат закрыт. Незалогиненный пользователь видит только форму входа.

### Первый запуск

1. В `.env` укажите логин будущего администратора и секрет сессии:

   ```
   ADMIN_LOGINS=ivan
   SESSION_SECRET=<длинная случайная строка>
   ```

   Секрет генерируется так:

   ```bash
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

2. Запустите сервер и зарегистрируйтесь на `/register` под этим логином —
   аккаунт сразу получит права администратора и доступ к чату.

Логин из `ADMIN_LOGINS` получает админку тем, что первым его занимает. Если
сервис уже смотрит в интернет, безопаснее завести админа заранее, до открытия
регистрации:

```bash
python manage.py create-admin ivan
```

### Как это работает

1. Новый пользователь регистрируется на `/register` и получает статус
   **ожидает** — чат ему недоступен, он видит страницу ожидания.
2. Администратор открывает `/admin`, видит заявку и нажимает **Подтвердить**.
3. Пользователь обновляет страницу и попадает в чат.

Статусы: `pending` (по умолчанию), `approved`, `blocked`. Снять доступ у самого
себя нельзя — защита от того, чтобы остаться без администратора.

### Служебные команды

```bash
python manage.py list                  # кто есть и с каким статусом
python manage.py create-admin <логин>  # завести администратора
python manage.py set-password <логин>  # сменить пароль (забытый в том числе)
python manage.py approve <логин>       # открыть доступ мимо веб-админки
```

### Как устроена защита

- Пароли хранятся как scrypt-хеши с индивидуальной солью (16 МБ памяти на
  проверку — перебор на видеокартах дорог). Наружу хеши не отдаются никогда.
- Ответ «Неверный логин или пароль» одинаков и для чужого логина, и для
  неверного пароля — форма не подсказывает, какие логины заняты.
- После 8 неудачных попыток логин блокируется на 5 минут. Счётчик живёт
  **в памяти процесса**: при нескольких воркерах uvicorn каждый считает свой,
  рестарт обнуляет. Для публичного сервиса этого мало — ограничение стоит
  продублировать на уровне nginx.
- Сессия — подписанная кука на 14 дней. На проде за TLS переключите
  `https_only=True` в `web.py`.

Пользователи лежат в SQLite (`app.db`, создаётся сам, в `.gitignore`).

## Вход через Яндекс (опционально)

Код входа через Яндекс OAuth в проекте есть, но включается только когда заданы
ключи — до этого кнопки на странице входа просто нет. Регистрация приложения
требует домена, поэтому этот способ имеет смысл включать после публикации.

На [oauth.yandex.ru/client/new](https://oauth.yandex.ru/client/new): платформа
**Веб-сервисы**, Redirect URI `https://ваш-домен/auth/callback`, права
`login:info` и `login:email`. Затем в `.env`:

```
YANDEX_CLIENT_ID=<ID приложения>
YANDEX_CLIENT_SECRET=<пароль приложения>
YANDEX_REDIRECT_URI=https://ваш-домен/auth/callback
```

Пользователи из Яндекса проходят то же подтверждение админом, что и обычные.

## Структура

```
llm.py            — клиент к API: обычный вызов и потоковый, телеметрия
web.py            — веб-сервер: маршруты, SSE-стриминг, сборка ограничений
auth.py           — пароли (scrypt), защита от перебора, Яндекс OAuth
manage.py         — служебные команды: админ, пароль, список
db.py             — SQLite: пользователи и их статусы доступа
static/           — интерфейс: чат, вход, ожидание, админка
app.py            — консольный чат
compare.py        — сравнение ответов с ограничениями и без
requirements.txt  — зависимости
.env.example      — шаблон конфигурации
.gitignore        — исключает .env и мусор
```
