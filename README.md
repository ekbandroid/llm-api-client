# llm-api-client

Чат с LLM через OpenAI-совместимый API: консольный и веб-интерфейс с потоковым ответом.
Плюс два режима сравнения — влияние ограничений на ответ и четыре способа рассуждения.

## Установка

```bash
git clone https://github.com/ekbandroid/llm-api-client.git
cd llm-api-client

python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install -r requirements.txt
```

## Настройка

```bash
cp .env.example .env
```

Откройте `.env` и впишите свой ключ. Файл `.env` в `.gitignore`, в репозиторий он не попадёт.

## Запуск

```bash
python app.py
```

## Другие провайдеры

Приложение работает с любым API, совместимым с форматом OpenAI. Меняются только две переменные в `.env`:

| Провайдер | `LLM_BASE_URL` | `LLM_MODEL` |
|---|---|---|
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| DeepSeek | `https://api.deepseek.com` | `deepseek-flash` (дешёвая) / `deepseek-v4-pro` |
| OpenRouter | `https://openrouter.ai/api/v1` | `anthropic/claude-sonnet-4.5` |
| Ollama (локально) | `http://localhost:11434/v1` | `llama3.2` |

Названия моделей меняются — актуальные смотрите в документации провайдера.

## Сравнение ответов: без ограничений и с ограничениями

```bash
python compare.py                          # вопрос по умолчанию
python compare.py "ваш вопрос"             # свой вопрос
```

Скрипт отправляет **один и тот же вопрос дважды** и печатает оба ответа с таблицей метрик.

| | Без ограничений | С ограничениями |
|---|---|---|
| Формат | не задан | жёсткая схема ТЕЗИС / ПРИЧИНЫ / ВЫВОД в системном промпте |
| Длина | не задана | лимит 80 слов в промпте + `max_tokens=250` на стороне API |
| Завершение | по усмотрению модели | `stop=["###END###"]` + инструкция вывести этот маркер |

Ограничения задаются на двух уровнях, и это не дублирование: инструкция в промпте
заставляет модель *планировать* короткий ответ, а `max_tokens` и `stop` — страховка
на стороне API на случай, если инструкцию проигнорируют.

Поле `finish_reason` в таблице показывает, чем кончилась генерация: `stop` — модель
завершила ответ сама, `length` — упёрлась в `max_tokens` и ответ оборван на полуслове.

### Подводный камень с thinking

У рассуждающих моделей (вся линейка DeepSeek v4) `max_tokens` ограничивает
рассуждение и ответ **вместе**. При включённом thinking рассуждение съедает весь
бюджет, и приходит пустой `content` с `finish_reason: length`. Причём отсутствие
поля `thinking` в запросе такую модель не выключает — нужно явно передать
`{"type": "disabled"}`, что и делает `llm.py`. Поэтому `compare.py` считает
без thinking: иначе сравнение длины ответов теряет смысл.

## Веб-интерфейс

```bash
uvicorn web:app --reload
```

Откройте http://127.0.0.1:8000

Ответ приходит **потоком** (SSE): текст появляется по мере генерации, а не после
полной готовности. На запросах в десятки секунд это принципиально меняет ощущение
от интерфейса.

Все ограничения из раздела выше выставляются прямо на странице:

| Панель | Что задаёт | Куда уходит |
|---|---|---|
| Модель | какая модель отвечает | поле `model` запроса |
| Режим thinking | рассуждать или нет | `thinking: {"type": ...}` |
| Формат ответа | пресет или своя инструкция | системный промпт |
| Лимит слов | «не более N слов» | системный промпт |
| `max_tokens` | жёсткий потолок генерации | параметр API |
| Стоп-последовательность | где оборвать | `stop` + инструкция в промпте |

Под каждым ответом — телеметрия: `finish_reason`, расход токенов, число слов,
время. Собранный системный промпт показан там же в сворачиваемом блоке, так что
видно, во что именно превратились выставленные переключатели. Если генерацию
оборвал `max_tokens`, выводится предупреждение — при включённом thinking с этим
сталкиваешься быстро.

История диалога живёт **только в памяти вкладки**: сервер не хранит ничего,
перезагрузка страницы очищает переписку. Состояния на сервере нет вовсе — весь
диалог приходит с каждым запросом.

## Четыре способа рассуждения

```bash
python reasoning.py                          # пример по умолчанию
python reasoning.py "задача" "эталон"        # своя задача
python reasoning.py "задача" "эталон" 5      # плюс 5 прогонов на устойчивость
```

В вебе то же самое живёт на `/reasoning`: задача вводится вручную, результат
каждого способа появляется по мере готовности, не дожидаясь остальных.

Одна задача решается четырьмя способами:

| Способ | Как устроен | Вызовов |
|---|---|---|
| Прямой ответ | системный промпт по умолчанию, никаких указаний | 1 |
| Пошагово | требование разбить решение на нумерованные шаги | 1 |
| Промпт от модели | первый вызов пишет промпт, второй решает по нему | 2 |
| Группа экспертов | аналитик, инженер и критик независимо, затем сведение | 4 |

Эксперты вызываются **отдельными запросами** намеренно: в одном общем промпте
критик видит ответ аналитика и склонен с ним соглашаться, независимой проверки
не получается.

**Thinking выключен во всех способах.** Иначе модель рассуждает внутри себя
независимо от промпта, разница между «прямым ответом» и «пошагово» смазывается,
и сравнивать мы будем работу thinking, а не промпты.

### Как читать результат

Ответ каждого способа разбирается до краткой формы и, если задан эталон,
сверяется с ним. У прямого способа метки `ОТВЕТ:` нет по условию задачи —
для него ответ ищется эвристикой: строка со словом «ответ», иначе последняя
строка с числом.

Один прогон о точности не говорит: модель недетерминирована и на одной задаче
отвечает по-разному. Третий аргумент командной строки задаёт число повторов —
тогда выводится доля верных ответов по каждому способу.

## Температура

```bash
python temperature.py                             # пример по умолчанию
python temperature.py "запрос" "эталон"           # свой запрос
python temperature.py "запрос" "эталон" 5         # 5 выборок на каждую температуру
```

В вебе — на `/temperature`, там же настраиваются список температур и число выборок.

Один и тот же запрос выполняется при разных температурах (по умолчанию 0, 0.7 и
1.2), **каждая — несколько раз**. Одной выборки недостаточно: температура влияет
прежде всего на разброс, а разброс по единственному ответу измерить не с чем.

| Метрика | Что показывает |
|---|---|
| Точность | доля выборок, совпавших с эталоном; без эталона не считается |
| Разных ответов | сколько среди выборок различных по краткому ответу |
| Разнообразие | 1 минус средняя попарная доля общих слов: 0 — тексты совпадают, 1 — ни одного общего слова |
| Уник. слов | доля неповторяющихся слов внутри ответа |

Креативность числом не измеряется — «уник. слов» лишь косвенный признак
непредсказуемости формулировок. Сами тексты выводятся целиком, судить о них
приходится глазами.

Thinking выключен: рассуждение сглаживает влияние температуры на итоговый ответ.

### Для каких задач какая температура

| t | Куда |
|---|---|
| 0 | факты, классификация, разбор в структуру, код — всё с единственным верным ответом; воспроизводимость между запусками |
| 0.7 | разговор, объяснения, переписывание текста, черновики — значение по умолчанию, когда не понятно, что выбрать |
| 1.2 | мозговой штурм, названия, слоганы, варианты сюжета; цена — растущий риск выдумок, факты обязательно проверять |

Температура 0 **не гарантирует** одинаковый ответ. Она убирает случайность
выбора токена, но не расхождения на стороне провайдера: на коротком слогане три
выборки при 0 совпали дословно, а на развёрнутом ответе про iPhone разошлись
(разнообразие 0.405 при том же нуле).

## Сравнение моделей

```bash
python benchmark.py                        # запрос по умолчанию
python benchmark.py "запрос" "эталон"      # свой запрос
```

В вебе — на `/models`, там набор конфигураций и цены настраиваются.

Один и тот же запрос выполняется в нескольких конфигурациях. Конфигурация —
это **модель плюс режим рассуждения**: одна и та же модель с включённым
thinking тратит на ответ заметно больше вычислений, и это такая же ступень
мощности, как переход на модель посильнее. Набор по умолчанию:

| Ступень | Конфигурация |
|---|---|
| слабее, дешевле | `deepseek-flash` |
| сильнее | `deepseek-v4-pro` |
| сильнее всего, дороже | `deepseek-v4-pro` + thinking |

### Что замеряется

| Метрика | Смысл |
|---|---|
| Время ответа | зависит и от модели, и от длины ответа — само по себе мало о чём говорит |
| Токенов в секунду | скорость генерации, очищенная от длины ответа; именно её и стоит сравнивать |
| Вход / выход | входные и выходные токены тарифицируются по-разному |
| Токены рассуждения | часть выходных, потраченная на размышление; оплачиваются, но пользователю не видны |
| Стоимость | вход × цена входа + выход × цена выхода |
| Качество | доля совпадений с эталоном, если он задан |

Цены подставляются из [тарифов DeepSeek](https://api-docs.deepseek.com/quick_start/pricing)
и правятся прямо в интерфейсе; изменённые сохраняются в браузере. По умолчанию
взяты **пиковые ставки без попадания в кэш** — верхняя граница, чтобы оценка не
оказалась заниженной. В непиковые часы вдвое дешевле, а при попадании в кэш
входные токены дешевле примерно в тридцать раз.

### Что показал прогон

На задаче про число нулей в конце 100! все три конфигурации ответили верно —
по качеству они не разошлись, задача для моделей несложная. Разошлись
в стоимости: 0.000224, 0.000461 и 0.000993 доллара, то есть в 4.4 раза между
крайними. При этом `flash` генерировал вдвое быстрее по токенам в секунду,
а `pro` уложился в наименьшее число токенов — то есть более дорогая модель
оказалась лаконичнее и разрыв в деньгах вышел меньше, чем разрыв в тарифах.

## Что уходит в API

В каждом режиме под ответом есть сворачиваемый блок **«Запрос к API»** — там
показано ровно то, что приложение отправляет: метод, адрес, заголовки и тело
запроса со всеми параметрами. Видно, во что превратились переключатели
интерфейса: какая модель выбрана, включён ли `thinking`, какая температура
подставлена, какие заданы `max_tokens` и `stop`.

Ключ API там заменён на `Bearer ***` — он передаётся заголовком и в браузер
не попадает.

При ошибке рядом с текстом появляется **«Ответ API (ошибка)»** — тело ответа
сервера целиком: код состояния и разобранный JSON с причиной отказа. У сетевых
сбоев ответа нет вовсе, и блок тогда не показывается.

Если ответа не было вовсе — соединение не установилось, оборвалось или истекло
время, — показывать нечего: JSON не существует. Вместо него выводится блок
**«Диагностика сбоя»** с типом исключения, адресом, таймаутом и пояснением.
Называть это «ответом» было бы неправдой: отвечать было некому.

Отдельно разбираются сбои, которые случаются **до** приложения: например `413`
отдаёт nginx, когда тело запроса тяжелее 1 МБ, и до сервера запрос не доходит
вовсе. Тело у такого ответа — HTML, а не JSON; блок называется «Ответ сервера
(ошибка)» и показывает его как есть, вместе с пояснением, что именно произошло.

Неудавшийся обмен не остаётся в истории: вопрос удаляется из диалога. Иначе
каждая неудачная попытка засоряла бы переписку навсегда и заново оплачивалась
в каждом следующем запросе.

Рядом лежит второй блок — **«Ответ API»** — с тем, что вернул провайдер:
идентификатор запроса, модель, `finish_reason`, `usage` с разбивкой по токенам
и попаданиям в кэш. **Сам текст ответа из JSON вырезан**: он уже отрисован
выше, а в сыром виде только мешал бы разглядеть служебные поля. Вместо текста
остаётся его длина.

В чате ответ приходит потоком, и единого JSON провайдер не присылает вовсе:
идут десятки кусков вида `chat.completion.chunk`, в каждом несколько символов
текста, а `usage` и `finish_reason` — только в последнем. Показывать последний
кусок бессмысленно (там пустой `delta.content`), показывать все — их сотни,
поэтому приложение **склеивает их в один ответ** обычного вида
`chat.completion`: служебные поля из первого куска, текст и причина остановки —
накопленные. В примечании указано, из скольких кусков он собран, чтобы блок
нельзя было принять за настоящий ответ провайдера.

У способов рассуждения, где вызовов несколько, блоки называются «Запросы к API (N)»
и «Ответы API (N)» и показывают каждый вызов отдельно: у способа с группой
экспертов их четыре.

### Служебные вызовы

Ответом дело не заканчивается: после него приложение обращается к модели ещё
раз — обновить карточку фактов, собрать конспект, решить, не пора ли менять
этап задачи. В режиме задачи со стратегией «Факты + N» таких вызовов два на
каждый обмен, и по расходу они сопоставимы с самим ответом:

| Вызов | Когда | Замеренная цена |
|---|---|---|
| Карточка фактов | стратегия «Факты + N» | 739–2 131 токен |
| Конспект | стратегия «Конспект + хвост», раз в 10 сообщений | ~1 000 |
| Переключатель этапов | режим задачи с автопереключением | 1 002–1 447 |

Раньше от них оставалась только строка с ценой. Теперь у каждого свои два
блока — «Запрос к API (карточка фактов)», «Ответ API (переключение этапа)» и
так далее, — и видно, что именно туда ушло: состояние, карточка и последний
обмен.

У этих ответов текст **не вырезается**, в отличие от основного: тут он и есть
результат — сама карточка фактов или решение переключателя, которое больше
нигде не показано.

Блоки сохраняются вместе с сообщением и остаются после перезагрузки. Цена —
около 9,5 КБ в поле `meta` на обмен; кнопка «Отменить» у автоматического
перехода живёт только до перезагрузки, потому что у сохранённого сообщения она
отменяла бы уже не тот переход.

В чате оба блока сохраняются вместе с сообщением, поэтому доступны и после
перезагрузки страницы.

## Разметка в ответах

Ответы моделей показываются с разметкой markdown: заголовки, списки, таблицы,
цитаты, блоки кода, жирный и наклонный текст, ссылки. Работает во всех режимах.

Конвертер написан вручную ([static/markdown.js](static/markdown.js)), без
внешних библиотек, и устроен в строгом порядке: **сначала экранируется весь
HTML, и лишь затем добавляются теги, которые формирует сам конвертер**. Это
принципиально: ответ модели содержит то, что ввёл пользователь, и наивная
вставка HTML открыла бы XSS. Разметка из самого ответа в документ попасть не
может, а ссылки принимаются только с `http` и `https` — `javascript:` и `data:`
остаются обычным текстом.

Поддерживается подмножество markdown, которое реально встречается в ответах
моделей. Сложные случаи — вложенные списки, ссылки-сноски, HTML внутри
markdown — не поддерживаются намеренно: они не встречаются, а каждая
дополнительная возможность конвертера это дополнительная поверхность для ошибок.

## Диалоги и сохранение контекста

Главная страница — чат со списком диалогов. Переписка и настройки лежат в SQLite,
поэтому после перезапуска приложения диалог продолжается с того же места: модель
помнит всё, что было сказано раньше.

| | |
|---|---|
| Список диалогов | вкладка слева, свежие сверху, с числом сообщений |
| Название | берётся из первого сообщения, правится вручную |
| Настройки | модель, thinking и `max_tokens` принадлежат диалогу и сохраняются с ним |
| Удаление | вместе с сообщениями, каскадом по внешнему ключу |

### Когда модель не отвечает

Провайдер может принять запрос, ответить `200` и держать соединение служебными
пакетами `: keep-alive`, не присылая ни одного куска текста. Обычный таймаут
чтения в этом случае бесполезен: данные формально идут.

Поэтому есть отдельный предел на **первый** кусок ответа — 60 секунд. Пока его
нет, в чате показывается, что модель молчит и сколько уже идёт ожидание; по
истечении приходит внятная ошибка вместо пустого экрана.

Список моделей приходит от API и меняется без нашего участия, поэтому рядом с
выбором модели есть кнопка **↻** — она перечитывает список у провайдера и
сообщает, что изменилось.

### Боковая панель

Панель собрана из вкладок: узкая полоса иконок слева видна всегда, рядом
раскрывается колонка с содержимым. Вкладки три — диалоги, настройки модели и
контекста, расход токенов. Повторный щелчок по иконке раскрытой вкладки
сворачивает панель до одной полосы.

Содержимое вкладки прокручивается внутри себя, наружу панель не растёт: в
диалогах прокручивается список, а кнопка «Новый диалог» остаётся на месте.
Полоса иконок прокручивается сама, если вкладок станет больше, чем помещается
по высоте.

Выбранная вкладка и то, свёрнута ли панель, запоминаются в браузере: это
удобство конкретного пользователя, а не свойство диалога, поэтому на сервер
не уходит.

### Как устроено

Клиент присылает только `conversation_id` и текст нового сообщения — **историю
поднимает сервер**. Это не просто удобнее: клиент не передаёт историю и потому
не может её подменить.

Владелец проверяется в каждом запросе условием `user_id = ?` прямо в SQL. Чужой
диалог отвечает `404`, а не `403`: иначе перебором идентификаторов можно было бы
узнать, какие диалоги существуют.

Вместе с ответом сохраняется его телеметрия — расход токенов, `finish_reason`,
время и описание запроса к API. Поэтому после перезагрузки страницы под каждым
ответом остаются те же аккордеоны и та же строка замеров, что и при получении.

Ограничения на длину истории пока нет: в API уходит вся переписка целиком.

**`max_tokens`** ограничивает только ответ, а не историю. Пустое поле означает
«без лимита»; если ответ упёрся в потолок, приходит `finish_reason: length`
и под ответом появляется предупреждение, что он не дописан. При включённом
thinking рассуждение расходует этот же бюджет — он может закончиться до того,
как модель начнёт писать ответ.

### Старый чат

Прежняя версия с ограничениями формата, длины и завершения осталась на `/legacy`
и работает по-старому — без сохранения, диалог живёт только в памяти вкладки.

## Подсчёт токенов

Страница `/tokens` разбирает любой диалог: сколько стоил каждый обмен, как
растёт расход и сколько будет стоить следующий запрос. Счётчик расхода есть
и в самом чате, в боковой панели.

Считаются три величины:

| Величина | Откуда |
|---|---|
| Ответ модели | `usage.completion_tokens`, точно |
| Текущий запрос | `usage.prompt_tokens` — это вся история на тот момент, точно |
| Следующий запрос | оценка по числу символов, до вызова точной цифры нет |

Точные числа сохраняются вместе с сообщением, поэтому разбор доступен и через
неделю после разговора.

### Почему оценка, а не точный счёт

До вызова API точное число токенов получить неоткуда: токенизатор у провайдера
свой. Оценка считается по символам, но коэффициент подбирается по составу
текста — единый врал бы почти вдвое. Коэффициенты измерены запросами к этому
же API:

| Текст | Символов на токен |
|---|---|
| Русский | 3.33 |
| Английский | 5.85 |
| Код | 2.41 |

Одна и та же мысль по-русски обходится почти вдвое дороже, чем по-английски.
На коротких репликах оценка отклоняется от факта до 25 процентов, на длинных
заметно точнее. Алгоритм продублирован в `tokens.py` и `static/common.js` —
в чате он должен давать ту же цифру, что на странице разбора.

### Что показал замер

Диалог из десяти коротких вопросов об устройстве API:

| Обмен | Вход | Выход | Накопительно |
|---|---|---|---|
| 1 | 22 | 18 | $0.000028 |
| 5 | 1 391 | 482 | $0.002936 |
| 10 | 5 084 | 248 | $0.012061 |

Вопросы одинаково короткие, но **входные токены выросли в 231 раз**: каждая
реплика заново отправляет всю переписку. Поэтому суммарный расход растёт
примерно как квадрат числа обменов, а не линейно.

### Что ломается

**Не контекст.** Заявленный предел обеих моделей DeepSeek — 1 млн токенов, но
порог мягкий: проверочный запрос на **1 028 577** токенов прошёл успешно,
HTTP 200.

**Деньги и время.** Тот же запрос стоил **31 цент** и занял **27 секунд**
только на передачу — это одна реплика. Длинный диалог становится непригодным
из-за цены и задержки задолго до любого технического предела.

**Одна реплика больше 1 МБ.** nginx отвечает `413` раньше приложения. Длину
диалога это не ограничивает: историю подставляет сервер, в теле запроса едет
только новая реплика.

## Стратегии управления контекстом

В настройках диалога выбирается, как собирается запрос из переписки, и **N** —
сколько последних сообщений уходит дословно (по умолчанию 10).

| Стратегия | Что уходит в запрос | Служебные вызовы |
|---|---|---|
| Вся история | вся переписка целиком | нет |
| Последние N | только последние N сообщений, остальное отброшено | нет |
| **Факты + N** (по умолчанию) | карточка ключ-значение и последние N | после каждого обмена |
| Конспект + хвост | конспект свёрнутой части и хвост | по накоплении 10 сообщений |

Новый диалог заводится со стратегией «Факты + N»: её карточка переживает
обрезку хвоста и, если диалог принадлежит проекту, перетекает в память проекта.

Страница `/strategies` задаёт один вопрос по каждой стратегии и показывает
ответы рядом с расходом.

### Замер на сценарии сбора ТЗ

Диалог из 22 сообщений, вопрос «Назови моё имя, срок, бюджет и платёжную
систему» — один и тот же для всех стратегий:

| Стратегия | Вход | Дословно | Свёрнуто | Отброшено | Помнит |
|---|---|---|---|---|---|
| Вся история | 9 438 | 22 | — | — | 4/4 |
| Последние N | 5 368 | 10 | — | 12 | 4/4 |
| Факты + N | 5 897 | 10 | — | 12 | 4/4 |
| **Конспект + хвост** | **3 956** | 6 | 16 | — | 4/4 |

Конспект оказался дешевле всех — на 58% меньше полной истории — и при этом
ничего не забыл.

### Три оговорки, без которых выводы будут неверными

**Окно сохранило факты случайно.** Проверка содержимого окна показала, что имя,
срок и бюджет в нём есть — но не из реплик пользователя, а потому что модель
сама повторяла требования в своих ответах. Без такого эха окно потеряло бы
начало разговора.

**Карточка фактов обходится дороже, чем экономит.** Она обновляется отдельным
вызовом после каждого обмена: на сценарии из 10 обменов это 28 979 служебных
токенов против 3 600 сэкономленных. Стратегия окупается только там, где
переписка гораздо длиннее, а фактов немного.

**Накопительные суммы по отдельным прогонам несопоставимы.** В каждом прогоне
своя история: модель отвечает репликами разной длины, и они же попадают в
историю. Корректно сравнивать только один и тот же вопрос на одном диалоге —
как в таблице выше.

### Ветки

Ветвление — отдельная ось: это структура диалога, а не способ сборки запроса.
Под каждым ответом есть кнопка **«⑂ Ветка отсюда»**: она копирует диалог до
этого сообщения включительно в новый, помеченный в списке символом `↳`.

Ветка — копия, а не общее дерево. Так две ветки развиваются полностью
независимо, удаление одной не задевает другую, и весь остальной код работает с
веткой как с обычным диалогом. Цена — дублирование уже сказанного; на здешних
объёмах это дешевле, чем усложнять выборку сообщений во всех запросах.

Проверено: две ветки от одного сообщения, в одной СУБД поменяли на MySQL, в
другой платёжную систему на Сбербанк — исходный диалог и соседняя ветка не
изменились.

## Модель памяти

Память агента разделена на три слоя. Они различаются не форматом, а сроком
жизни и владельцем — и хранятся порознь, каждый в таблице своего владельца:

| Слой | Что помнит | Где лежит | Живёт | Кто наполняет |
|---|---|---|---|---|
| **Краткосрочная** — диалог | сообщения, конспект, карточка фактов | `messages`, `conversations` | до удаления диалога | приложение |
| **Рабочая** — проект | бриф задачи и факты, накопленные из диалогов проекта | `projects` | пока жив проект | пользователь + перелив фактов |
| **Долговременная** — профиль | кто пользователь, как ему отвечать, чего держаться | `profiles` | постоянно | пользователь |

Общей таблицы памяти нет намеренно: при таком делении каскадное удаление
получается даром (удалили проект — ушла его рабочая память), и ни один запрос
не начинается с фильтра по типу слоя.

### Что куда уходит

Каждый слой уходит в запрос **отдельным system-сообщением**, в порядке от
постоянного к сиюминутному:

```
system  базовый системный промпт
system  Долговременная память. Профиль «…»: о собеседнике, стиль, ограничения
system  Рабочая память. Проект «…»: описание задачи + накопленные факты
system  Известные факты о задаче и собеседнике: …   (краткосрочный слой)
…последние сообщения диалога…
```

Раздельными, а не одной склейкой: так слой виден в аккордеоне «Запрос к API»
сам по себе и любой можно отключить, не пересобирая остальные. Под ответом
модели сразу, ещё до текста, появляется строка «Память в запросе: профиль
~27 токенов; проект «X» ~71 токенов, фактов 4» — видно, что именно ушло.

Блок проекта уходит и тогда, когда проект пуст: в нём остаётся название и
строка «Пока о проекте ничего не записано — не домысливай за него». Иначе
первый обмен в новом проекте шёл бы вообще без рабочего слоя — бриф ещё не
написан, а факты появляются только после ответа, — и со стороны это выглядело
как несработавшая галочка.

Управление явное: профиль и бриф пишутся руками во вкладке **«Память»**, там же
у каждого слоя флажок «подключать к этому диалогу». Диалог заводится сразу
внутри проекта — кнопкой **«+ диалог»** в его группе; список диалогов теперь
сгруппирован по проектам, а те, что были заведены раньше, лежат в группе
«Без проекта».

Объёмы ограничены: профиль и бриф — по 4000 символов, фактов у проекта не
больше 40, у диалога — 25. Слой уходит в каждый запрос и оплачивается заново,
поэтому счётчик токенов у каждого поля показывает цену прямо при вводе.

### Перелив фактов

При стратегии «Факты + N» карточка диалога после каждого обмена сливается в
память проекта: новые ключи добавляются, изменившиеся заменяют прежние. К
модели за этим не обращаемся — факты уже извлечены при обновлении карточки
диалога, платить второй раз не за что.

Проверено на двух диалогах одного проекта: в первом модель узнала имя, домен и
технологию, во втором — заведённом заново, с **отключённым** профилем —
ответила «Тебя зовут Иван. Твой сервис живёт по адресу llmchat.me.uk», то есть
исключительно из рабочей памяти проекта.

### Чем это ломается

**Диалог с «не знаю» отравляет память проекта.** В диалоге с отключёнными
слоями модель честно ответила, что не знает имени и адреса, — и карточка фактов
записала это как факт (`факты: ассистент не знает имя пользователя`), после чего
перелив утащил запись в проект. Там она встала рядом с верными значениями и
перебила их: следующий диалог, уже с подключённой рабочей памятью, снова ответил
«не знаю».

Починено в источнике: карточке фактов теперь прямо запрещено записывать
состояние ассистента — она описывает задачу и собеседника. Плюс любой факт
проекта убирается крестиком вручную.

**Ключи в разных диалогах называются по-разному.** Один диалог записал
`имя_пользователя`, другой — `имя`; в памяти проекта оказались обе записи с
одинаковым значением. Слияние идёт по точному совпадению ключа, синонимы оно
не распознаёт.

## Персонализация: профили

Долговременный слой — не один текст на пользователя, а **несколько профилей**:
у одного человека бывает несколько ролей, и отвечать в них надо по-разному.
Диалог ссылается на выбранный профиль и переключается на другой в любой момент —
список профилей стоит во вкладке «Память».

В профиле четыре поля:

| Поле | Зачем | Пример |
|---|---|---|
| О собеседнике | кто и над чем работает | `Роль: Senior Android Developer. Проект: мобильный банк, команда 4 человека.` |
| Стиль | как отвечать | `Краткие ответы. Формальный тон. С примерами кода на Kotlin.` |
| Ограничения | чего держаться | `Kotlin, Ktor, Coroutines. MVVM. Только бесплатные API. minSdk 26.` |
| Формат ответа | текст или JSON-объект | `response_format={"type": "json_object"}` |

Каждое текстовое поле — до 4000 символов. Все три уходят в запрос одним
system-сообщением с подписанными разделами: смешивать их в один абзац значит
получать ответы, где ограничения теряются среди биографии.

При первом запуске заводятся четыре готовых профиля — два Android и два
Python, — и они обычные: их правят, переименовывают и удаляют. Прежняя
единственная долговременная память переносится в профиль «Мой профиль» и
остаётся подключённой к старым диалогам.

Один и тот же вопрос «как сохранить токен авторизации?» в трёх профилях:

| Профиль | Ответ |
|---|---|
| Android: мобильный банк | `EncryptedSharedPreferences` с `MasterKey`, код на Kotlin |
| Python: бэкенд на FastAPI | `cryptography.fernet`, код на Python |
| Python: данные и отчёты | тот же смысл, но одним JSON-объектом |

### `response_format` в DeepSeek

Проверено запросами к живому API:

| `type` | Что происходит |
|---|---|
| `text` | работает, поведение по умолчанию |
| `json_object` | **работает**, в том числе в потоке и вместе с `thinking` |
| `json_schema` | HTTP 400 «This response_format type is unavailable now» |
| `regex` | HTTP 400, та же формулировка |

Жёсткую схему полей провайдер пока не отдаёт, поэтому структуру описываем
в промпте, а `response_format` гарантирует синтаксически корректный JSON без
```-ограды.

Главная ловушка: если формат `json_object`, а слова «json» нет ни в одном
сообщении, отклоняется **весь запрос**:

```
HTTP 400  Prompt must contain the word 'json' in some form
          to use 'response_format' of type 'json_object'.
```

Поэтому к блоку профиля добавляется строка «Отвечай строго одним
JSON-объектом…», а в `llm.build_payload` стоит подстраховка: если слова «json»
в сообщениях нет, оно дописывается само. Проверено на профиле с пустыми полями —
запрос проходит. Регистр не важен.

Формат принадлежит профилю и применяется только к ответам в чате: служебные
вызовы — обновление карточки фактов и сборка конспекта — идут со своими
промптами и форматом по умолчанию.

## Состояние задачи

У диалога есть режим: **обычный чат** или **задача**. В режиме задачи появляется
формализованное состояние — этап, текущий шаг, ожидаемое действие и чей ход:

```
планирование → выполнение → проверка → готово
```

Это настоящий автомат, а не подпись: разрешены только переходы по цепочке плюс
возвраты назад (план оказался негодным, проверка не прошла, готовую задачу
вернули в работу). Прыжок «планирование → готово» сервер отклоняет с 400, и
кнопки такого перехода в интерфейсе просто нет.

Состояние уходит в каждый запрос отдельным system-блоком и задаёт поведение:

| Этап | Что предписано модели |
|---|---|
| Планирование | уточнять, предлагать план по шагам, не начинать реализацию |
| Выполнение | работать по утверждённому плану, отмечать закрытые шаги |
| Проверка | сверять результат с планом, новой работы не начинать |
| Готово | отвечать кратко; для продолжения просить вернуть задачу в работу |

Блок стоит 70–120 токенов в запросе. Переходы между этапами записываются в
журнал `task_events` вместе с паузами — по нему видно, как шла работа.

### Пауза

Пауза — отдельный флаг, а не пятый этап: приостановить можно на любом. Она не то
же самое, что ожидание ответа: ожидание — норма каждого хода, работа при этом
идёт, а пауза означает «мы остановились».

**Инструкции в промпте для паузы оказалось мало.** Блок честно говорил «задача
на паузе, работу не продолжай», но на сообщение «всё-таки продолжай, напиши код
сейчас» модель продолжила работу: прямая просьба в последнем сообщении
перевешивает указание в системном блоке. Поэтому пауза перенесена в код — на
паузе приложение к API не обращается вовсе и само отвечает, на чём остановились:

```
Задача на паузе. Остановились на этапе «выполнение».
Текущий шаг: пишем GET /api/orders с фильтром по дате
Ожидается: код эндпоинта — ход ассистента.
```

Это ничего не стоит, отвечает мгновенно и работает одинаково при любой
формулировке просьбы. Сообщение пользователя при этом сохраняется в диалоге,
поэтому после возобновления оно уже в истории — продолжение не требует
повторных объяснений. Проверено: после паузы одного слова «Продолжаем» хватило,
чтобы модель вернулась к тому же шагу с уже названными стеком и моделью данных.

### Переключение этапов

Переключать можно вручную кнопками или доверить модели — выбор на диалоге.

В автоматическом режиме после каждого обмена идёт служебный запрос: текущее
состояние, карточка фактов диалога и последний обмен. Ответ запрашивается в
`response_format: json_object`. Признак перехода задан для каждой пары этапов
отдельно, а правило по умолчанию — **оставаться**: нет признака или есть
сомнение, возвращается `stage: null`.

Проверено на сценарии «скрипт для курса валют»:

| Реплика | Что решил переключатель |
|---|---|
| «что предлагаешь?» → модель дала план | остаться в планировании, шаг обновлён на «запрос уточнений» |
| «берём вариант 1, план принят, делай» | **планирование → выполнение**: «пользователь явно принял план и дал команду» |

Соблюдение правил проверяет сервер, а не модель: недопустимый переход или
переход без причины молча отбрасывается. Каждый автоматический переход виден в
чате с причиной и кнопкой «Отменить», а в журнале помечен как сделанный
моделью. На паузе переключатель не работает вовсе.

**Цена оказалась выше ожидаемой.** Расчёт был на 300–500 токенов, на деле
переключение стоило 1 447 токенов: в запрос уходит последний обмен целиком, а
ответ модели на этапе выполнения — это 715 токенов кода. То есть служебный
запрос дорожает вместе с длиной ответов, и на длинных ответах автоматический
режим заметно дороже ручного.
